# Purifier & AC Automations

**TL;DR**: The collector loop (every ~5s) runs two automation types — metric-based and schedule-based — for two device types: Xiaomi purifiers (`device_type='purifier'`) and TCL ACs (`device_type='ac'`). AC metric rules are a thermostat-hysteresis state machine (`checkAcRangeAutomation()`) with multi-range time slots, per-slot fan speed (incl. server-computed smart auto), diff-based re-enforcement, and persistent manual-off locks. AC presets (server-side, 10 slots) are the action source for AC rules; preset apply/save syncs into automations. Sticky beep-off and (since 2026-08-06) fan/vertical-swing drift are enforced separately each tick, outside that state machine. Leveler interaction points (generator_mode/fan stripping, shed vs manual-off) are documented here; leveler internals live in [ac-leveling.md](ac-leveling.md).

## Overview & device routing

- Two automation types (metric, schedule) are processed in the collector loop, configurable via dashboard. Supports both **purifier** (`device_type='purifier'`) and **AC** (`device_type='ac'`) devices. The `device_type` column on the `automations` table routes execution: purifiers → `xiaomiCloud.executeAction()`, ACs → `tclCloud.executeAcAction()`. (AC automation system added 2026-04-21.)
- Power state cache (`getDevicePowerCached`) queries the appropriate cloud based on device type: `fetchDevicesLive()` for AC (live shadow query) vs `getDevicePower()` for purifiers. 5s TTL.
- AC automations use **single-device selection** (radio buttons, not checkboxes).
- Key collector methods: `checkMetricAutomation` (purifier single-threshold), `checkAcRangeAutomation` (AC dual-threshold hysteresis), `checkScheduleAutomation`, `checkAcTimers`, `checkAcBeepEnforcement`, `checkAcRangeEnforcement` (fan/swing drift sweep), `executeAutomationAction` (routes to xiaomi or tcl based on `device_type`). These are the two separate code paths to remember when modifying automation logic: `checkMetricAutomation` (single-threshold, purifiers) vs `checkAcRangeAutomation` (dual-threshold hysteresis, AC).
- `automations` table fields: `id`, `automation_type` (metric/schedule), `device_type` (purifier/ac), `device_ids`, `device_names`, `metric`, `condition`, `threshold`, `threshold_low` (AC range hysteresis), `sustained_minutes` (metric type), `time_start`, `time_end`, `turn_off_at_end` (both types), `start_mode`, `start_prayer`, `start_prayer_offset`, `end_mode`, `end_prayer`, `end_prayer_offset` (schedule type), `action_on` (JSONB — purifier: `{power:"on"}`, AC: full preset profile `{power:1, mode, temperature, fan_speed, eco, turbo, screen, vertical_swing, horizontal_swing, fresh_air, generator_mode}`), `action_off`, `cooldown_secs`, `enabled`, `smart_leveling`, `range_slots`. Full schema in [database.md](database.md).
- **Rule cache invalidation**: collector caches automation rules for 30s; `collector.invalidateAutomationRules()` resets `automationRulesLastFetch=0` so the next tick (≤5s) reloads rules from DB. Routes wires this via the `onAutomationRulesChanged?.()` callback.
- **TCL Cloud auto-recovery** (added 2026-05-01): when a TCL 403 retry fails, `tokenData` stays null and `isReady()` returns false permanently — silently disabling ALL AC automations with zero log output. Root cause: the 403 handler sets `this.tokenData = null` before calling `ensureValidTokens()`; if re-auth fails, it stays null. Fix: collector's `checkAutomations()` attempts `tclCloud.init()` when `isReady()` is false, with a 60s retry cooldown. Diagnostic warnings were also added for unknown/null metrics in `checkAcRangeAutomation()`. TCL protocol details: [tcl-ac.md](tcl-ac.md).
- **Calibration suspension**: while `acCalibrator.isActive()` the collector skips ALL AC automations, AC timers (they stay pending and fire late), and the leveler tick — so calibration turn-offs never record manual-off locks. Beep enforcement is also skipped while calibration is active.
- **Why this system exists**: the user needed temperature-based AC control with hysteresis to prevent rapid cycling, plus quick timers for delayed on/off from the AC card.

## Metric-based (purifier)

- AQI threshold triggers (e.g., PM2.5 above 50 → turn on purifier). Single threshold + condition (above/below).
- Supports `sustained_minutes` (condition must hold continuously before triggering).
- While the condition holds, re-checks device power every cooldown (default 5s) and re-sends turn-on if off.
- Optional `turn_off_at_end` (labeled "Turn off when resolved" in UI): when the condition clears, after a 60s grace period, sends power-off to all devices.
- **Cooldown = 5s** (changed 2026-04-25, was 300s) for both `checkMetricAutomation` and `checkAcRangeAutomation` — the collector acts on every loop tick (loop runs every 5s). New metric automations INSERT with `cooldown_secs=5` (routes.ts); existing rows were migrated via the `database.ts` MIGRATIONS list. Schedule automations remain at 60s.

## Metric-based (AC) — thermostat hysteresis

- Dual-threshold range: `threshold` = high limit, `threshold_low` = low limit; both support decimals.
- The AC trigger form supports a "Real temp" vs "Feels like" toggle for indoor temperature metrics (added 2026-04-25): maps `temp_indoor_c` → `feels_like_indoor_c` and `temp_ch8_c` → `feels_like_ch8_c` via `FEELS_LIKE_MAP` / `REVERSE_FEELS_LIKE` in `alerts-modal.tsx`. Both feels-like metrics exist in server + client `alert-metrics.ts`. When editing an existing rule, the form detects whether the stored metric is a feels-like variant and pre-selects the toggle.
- **Presets are the action source**: AC automations do NOT have a custom mode/temp/fan editor. The frontend reads saved presets from the server-side `ac_presets` table and copies the full `PresetData` (10 properties) into `action_on` JSONB with snake_case keys (mode, temp, fan_speed, eco, turbo, screen, vertical_swing, horizontal_swing, fresh_air, generator_mode) plus a `_preset_slot` reference. Presets must be saved in the AC widget first, then referenced when creating automations. When editing an automation, the form pre-selects the preset from `action_on._preset_slot`.
- The preset's **mode determines hysteresis direction**:
  - **Cool (mode=1)**: turns ON when temp >= high limit, turns OFF when temp <= low limit.
  - **Heat (mode=4)**: turns ON when temp <= low limit, turns OFF when temp >= high limit.
- Processed by `checkAcRangeAutomation()` in `server/src/collector.ts` — a state machine: IDLE → TRIGGERED at threshold limits; the dead zone re-enforces the profile (no power toggle). `AcAction.power` is optional — when undefined, `executeAcAction` sends only profile commands (no `set_power`, no restore delay). Cooldown is 5s (acts every loop tick).
- **Diff-based re-enforcement** (fixed 2026-04-25): dead-zone and triggered-state re-enforcement use `computeAcDiff()` — compares current device state with the desired profile and only sends properties that differ; skips the send entirely when everything matches. Previously it sent ALL 10 profile commands blindly every 5s.
- **Model-aware filtering** (the AC models are handled differently; full protocol details in [tcl-ac.md](tcl-ac.md)):
  - **Najat (TAC-24CHSA)**: `windSpeed7Gear`, `verticalWind`/`horizontalWind`, has `newWindSwitch` (fresh air). Does NOT have `ECO`, `turbo`, `silenceSwitch` — these are filtered out in `buildProfileShadowPayload`.
  - **Abdu/Abdullah (TAC-12CHSD)**: `windSpeed`+`silenceSwitch`+`turbo`, `verticalSwitch`/`horizontalSwitch`, has `ECO`. Does NOT have `newWindSwitch` — `set_fresh_air` is filtered out.
  - Model detection via `isNajatModel()` depends on `cachedDevices` being populated. `ensureDeviceCachePopulated()` is called in `executeAutomationAction()` for AC devices (added 2026-05-10), in the test endpoint, and before initial turn-on.
  - `executeAcAction` with power=1 + profile sends power and profile as two separate shadow updates with a 3s boot delay (NOT combined — Najat firmware quirk, see [tcl-ac.md](tcl-ac.md)).
  - **Fan-speed/turbo coupling** (hardened 2026-06-08): for non-Najat, the fan block owns `windSpeed`/`silenceSwitch`/`turbo` atomically (7=turbo, 1=silence; the shadow-derived `fanSpeed` reads 7 *because* `turbo===1`). ANY `fan_speed` in a profile drops the explicit `turbo` from `buildProfileShadowPayload`, and `computeAcDiff` skips the `turbo` comparison when desired `fan_speed` is present. **Why**: a preset's `turbo:0` + smart-auto-resolved fan 7 is self-contradictory on this model — the diff alternated `{turbo:0}`/`{fan_speed:7}` commands every 5s tick forever (the Abdu AC beeped every 5s, 2026-06-08). Manual-fan drift detection couldn't break the loop because each flip landed inside the 15s settle window of our own command. Regression tests in `tcl-cloud.test.ts`.
- **Shadow-reported gotcha** (discovered 2026-05-10): the AC may report (in shadow `state.reported`) that settings are applied even when physically they aren't. This affects `computeAcDiff()` — it reads reported state from cache and may see no diff when the physical AC doesn't match. The two-step power/profile approach (3s delay) mitigates this for initial turn-on. For re-enforcement, the diff catches settings that were later changed via remote control.
  - **A diff carrying `fan_speed` is self-sabotaging on TAC-12CHSD unless the fan is published alone** — the device applies the diff's other properties, resets the blower, reports the fan as applied, and the diff then reads clean forever. `executeAcAction` now splits the fan out of ANY multi-property payload (`splitFanPayload`); the 2026-07-27 post-changeover incident that forced this is written up in [tcl-ac.md](tcl-ac.md) → "the fan block must travel ALONE". Nothing downstream can detect a miss, so never rely on a re-enforcement tick to repair a fan.
- **Dead zone** (temperature between the limits):
  - If the AC is ON → diff-based re-enforcement: compares current device state with the desired profile via `computeAcDiff()`, only sends properties that differ (overrides manual remote changes without blind resends).
  - If the AC is OFF because the user manually turned it off, the collector records a device-level manual-off lock in `ac_manual_off_locks`. That lock blocks all AC auto-on paths until a manual-on is observed; temperature reaching the low/off limit must **NOT** unlock it (see Manual-off locks below).
- **Warm-restore hook** (automation-side call site, 2026-06-08): when the range automation auto-turns-off an AC because its temperature left the comfort range (the two `shouldTurnOff` branches in `checkAcRangeAutomation` — scoped to temperature cycling only, NOT time-window/schedule ends, NOT manual-off, NOT leveler sheds), the collector calls `acLeveler.rememberStableLevel(did)` BEFORE sending the off command. Leveler-side behavior of the remembered level: [ac-leveling.md](ac-leveling.md).

## Range slots & fan speed

- **Range slots** (`range_slots` JSONB, `AutomationRangeSlot` type in `server/src/automation-slots.ts`; added 2026-06 on branch codex/ac-manual-off-lock): one AC rule can hold **1–24 time-windowed ranges**, each with its own `threshold_low`/`threshold` pair. Windows are exact HH:MM or prayer-relative, overnight is supported, max one `all_day` fallback slot, no overlaps (`validateRangeSlots`).
  - `findActiveRangeSlot()` picks the active slot each tick; no active slot → `turnOffAcOutsideRange()` (the AC is turned off).
  - Legacy rules without `range_slots` convert via `getLegacyRangeSlots()`.
  - **Persistence choke point gotcha**: `normalizeRangeSlots()` whitelists slot fields — new slot fields MUST be added to the whitelist or they are silently dropped before storage.
- **Per-slot generator level** (`slot.gen_level`, optional; added 2026-06-10): `1–3` = level for that range (`MAX_GENERATOR_LEVEL`; was 1–6 until TCL removed Najat's 4–6 in 2026-06), absent = **Auto**. Validation rejects 0 (Auto = absent; level 0 = unrestricted footgun). Two behaviors:
  - **Leveler-managed device** (leveler enabled + `smart_leveling` true): the value rides the leveling tick context (`computeAcNeed` → `LevelerDeviceContext.slotGenCap`) as a **HARD CAP** — never raised above (beats boost floors; a live manual target still wins), reductions/sheds below stay allowed; a slot flip re-evaluates immediately. Leveler-side precedence details: [ac-leveling.md](ac-leveling.md).
  - **Unmanaged** (leveler off or rule opted out): `effectiveAcRangeProfile()` merges `generator_mode = min(gen_level, deviceMax)` into the profile (overriding the preset's `generator_mode`) at the turn-on + all 3 re-enforcement sites; diff re-enforcement retries it every 5s. (The historical "Najat L6 re-sends forever" caveat is closed since 2026-06-11: `clampGeneratorMode()` in tcl-cloud clamps every profile/diff gen level to the device max, and the max is 3 everywhere — see [tcl-ac.md](tcl-ac.md).)
    - **Manual gen change wins (2026-06-21):** a user's hand-set gen level on an unmanaged AC suppresses this re-enforcement so it isn't slammed back every 5s. `routes.ts` routes the control through `collector.onUserAcGenLevel()` (records `lastUserGenChangeAt`); `stripLeveledControls()` drops `generator_mode` whenever it SURVIVED `stripGenIfLeveled` (the leveler isn't managing the level) AND `hasRecentUserGenChange(deviceId)` is true. Bounded grace `AC_USER_GEN_OVERRIDE_MS` (**30 min**, resets on each manual change) so the automation reclaims if the override is forgotten — for a permanent change, set the slot's gen level to Auto. **Live trigger:** "leveling off but Abdu still drops to L1" — his "Feels Like (Abdu)" range was `smart_leveling=false` with slots pinned `gen_level=1`, slamming every manual L3 back to L1 within ~3s. (For a leveler-MANAGED AC, manual intent is the leveler's `manualCap`/`manualTarget` instead.)
  - UI: a "Gen" row (Auto + `L1..Lmax` from the selected AC's `maxGeneratorLevel`) in the slot editor, under the Fan row.
- **Per-slot vertical swing** (`slot.vertical_swing`, optional; added 2026-06-17): pins the AC's vertical air direction while that range is active. Valid set `{0,1,2,3,9,10,11,12,13}` (TCL vertical encoding: 0=Off/swing, 1=Full, 2=Up, 3=Down, 9=Top..13=Bottom). **Absent = the preset profile's `vertical_swing`** (falls through the `{ ...action_on }` spread). **Unlike `gen_level`, `0` (Off) is a VALID stored value**, not "Auto" — every guard uses `!= null` / `typeof === "number"`, never truthiness, so 0 survives normalize → save → profile merge (`VALID_VERTICAL_SWING` set in `automation-slots.ts`).
  - `effectiveAcRangeProfile()` sets `profile.vertical_swing = slot.vertical_swing` (overriding the preset's) at the turn-on + 3 re-enforcement sites; the turn-on `onAction` builder adds it too. Diff-gated by `computeAcDiff` (which already diffs `vertical_swing`), so it re-asserts within ~5s but does not beep-loop when the device already matches.
  - **Manual UI swing wins** (added 2026-06-18, parity with fan's intent model): a vertical-swing change from the AC card hits the control endpoint's `set_vertical_swing` branch → `onUserSwingChange` → `collector.noteUserAcSwingChange()`, which records a per-rule+device override in the `acSwingOverrides` map (keyed `${ruleId}:${deviceId}`, storing the active `slotId`). While that override is live, `effectiveAcRangeProfile()` **drops `vertical_swing` from the enforced profile** (it deletes the preset's value too), so the automation never re-asserts swing. The override clears — and enforcement resumes — only when the **active slot changes** (the stored `slotId` no longer matches, cleared inside `effectiveAcRangeProfile`) or the **AC power-cycles** (`clearAcSwingOverride` at all five `clearAcFanEnforcement` sites: turn-on, turn-off, observed-off, lock-check adopt, outside-range off — so a grid↔gen changeover that bounces the AC resets swing intent too). **No shadow-drift detection** (unlike fan): swing changes made from the physical remote / TCL app are NOT detected and still get re-asserted on the next tick — deliberate, because swing's power-loss reset value is unknown and would make drift misreads likely. (The 2026-08-06 enforcement sweep keeps this: it re-asserts swing only inside the post-power-cycle window, where a difference IS known to be a firmware reset — see "Fan & swing enforcement sweep".) No per-device clamp (swing values are model-agnostic; `sendControl` maps to the right `verticalWind`/`verticalSwitch` prop per model). Horizontal-only value `4` is excluded from the valid set.
  - UI: a "Swing" icon row (Preset default + the 9 `VerticalIcon` options, swing/fix divider) in the slot editor, under the Gen row. Icons + option list live in the shared `client/src/components/ui/swing-controls.tsx` (extracted from `ac-widget.tsx`'s `SwingSelector`).
- **Per-slot fan speed** (`slot.fan_speed`, optional; added 2026-06-06, default flipped 2026-06-11): `1–7` = fixed level for that slot; `0` **or absent** = **delta-based smart auto**. Since 2026-06-11 the range fan is ALWAYS smart auto unless the slot explicitly fixes 1–7 — **the preset's `fan_speed` no longer drives range enforcement at all** (user: "it should always be on A unless the user specify"; live trigger: Najat's preset fan 7 pinned her at max all cycle because her slot had no override). Presets still apply their fan on a manual tap, which then counts as a manual override until the slot changes / power cycles. `resolveRangeFan()` now always returns a level (never null).
  - **Smart auto** (`server/src/ac-auto-fan.ts`, `computeAutoFanLevel`, pure + unit-tested): cool delta = value − slot low (heat mirrors: slot high − value); ≤0.5° → L1, then +1 level per 0.3° (L2 ≤0.8°, L3 ≤1.1°, …), cap L7, with 0.1° down-hysteresis (raises immediate/instant, lowers only past the band). Range automations **never** send the AC's built-in fan auto (0).
  - Resolution happens in `resolveRangeFan()`/`effectiveAcRangeProfile()` in collector.ts, applied at all **4 profile sites** in `checkAcRangeAutomation()`: turn-on, lock-check adoption, dead-zone adoption, triggered re-enforcement.
- **Manual fan override — manual fan always wins**: a manual fan change (remote or UI) suspends fan **and turbo** enforcement (non-Najat fan 7 == turbo) for that rule+device until the active slot changes or the AC power cycles.
  - In-memory `acFanEnforcement` Map in the collector, keyed `${ruleId}:${deviceId}` — lost on restart by design (accepted, like leveler manual gen intents).
  - **Remote detection** in `updateAcFanTracking()`: shadow `fan_speed` drift vs the last-commanded fan, with a 15s settle window (`AC_FAN_SETTLE_MS`) so our own just-sent command isn't misread; the baseline is adopted when the observed fan already matches the desired one.
  - **Observed fan 0 is NEVER a manual intent (2026-06-11, mirror of the leveler's gen-level-0 rule):** TCL firmware resets the fan to built-in auto (0) after a power-loss restart (every changeover), and automations never command 0 — the old drift branch read that 0 as a manual change and suspended enforcement forever (live: Abdu & Abdullah stuck showing "A" after the gen→grid switch). A 0 observation is skipped; the next tick's diff re-sends the resolved fan. The dashboard **A button** stays the explicit way back to auto (`noteUserAcFanAuto` deletes the enforcement entries — intent, not drift). Accepted trade-off: a *remote*-set built-in auto is also overridden within ~5s.
  - **UI detection** is instant via the `set_fan_speed`/`set_turbo` hook in the routes control endpoint → `collector.noteUserAcFanChange()` (wired through `AcManualOffLockHandlers.onUserFanChange`), which also releases any leveler fan hold (`acLeveler.onUserFanChange`).
  - **UI fan Auto is the resume switch** (2026-06-07): `set_fan_speed` with value 0 routes to `onUserFanAuto` → `collector.noteUserAcFanAuto()` — deletes the device's `acFanEnforcement` entries (clears the manual override) and releases any leveler fan hold, so the automation's resolved fan (smart auto for Auto slots/presets) re-enforces on the next tick (within ≤5s). The AC's built-in auto only sticks/persists on devices no automation owns. Note: a *remote*-set auto still reads as a manual change via drift — only the dashboard A (Auto) button resumes enforcement.
  - All off paths (range off, observed off, outside-range off) and automation turn-on clear the fan-enforcement bookkeeping — **but only the cycles the RULE drives**. Leveler and power-event cycles are covered separately since 2026-08-06; see "Power-cycle clear sites" below.
  - **Leveler fan holds override fan enforcement** (2026-06-06 evening): while the leveler holds an AC's fan (last try before a shed — see [ac-leveling.md](ac-leveling.md)), enforcement defers entirely: `stripLeveledControls(rule, action, deviceId)` (the deviceId-aware wrapper around `stripGenIfLeveled`) drops `fan_speed`+`turbo` at all 4 profile sites, `updateAcFanTracking` early-returns (a hold is not a manual change), and every leveler fan command re-stamps `lastCommandedFan`/`lastFanCommandAt` via `refreshAcFanBaseline()` so neither the hold nor its release trips false manual-change detection. After the hold releases, the automation re-takes fan control as a normal diff.

## Manual-off locks

Persistent device-level user intent stored in `ac_manual_off_locks` (`device_id TEXT PRIMARY KEY`, `locked_at TIMESTAMPTZ`, `reason TEXT` — schema in [database.md](database.md)). The table prevents deploys/restarts from clearing a user's manual-off choice.

- **`recordAcManualOff()`** is called for: UI `set_power=0`, detected physical/remote off while an AC automation had seen the device on, and turn-off timers.
- **Observed-off classification (2026-07-06 — power events are NOT manual offs).** Blackouts, changeovers, and gen brownouts turn ACs off, and TCL shadows can lag the event by MINUTES (13 min observed live) — two bogus `observed_off` locks stranded a hot room overnight (2026-07-05/06: a 23s blackout at 08:00 → lock at 08:13; a gen brownout at 23:44 → lock all night). All three observed-off sites (metric, range, schedule) now route through `handleObservedAcOff()` in `collector.ts`, which classifies before locking:
  - **Commanded-off guard (2026-07-06 evening — a manual off from ANY source must stick):** a device that is ALREADY manual-off locked short-circuits the whole classification — a UI off / turn-off timer records its lock BEFORE the shadow ever shows the off, so an existing lock means the user's own commanded off, never a power event. Returns false (lock kept, no re-record, no push). **Live regression this fixed:** on gen with constant collapse/ESP-gap stamps the window was always active, so every dashboard off was reclassified power-event → re-ON → our own ON cleared the lock 18s later (Najat, 4× in 5 min).
  - **Negative power-cycle fingerprint (2026-07-06 evening, beats the window):** an OFF shadow still showing `beep: false` on a beep-off-enforced AC proves the unit never lost power (firmware resets beepSwitch to ON on EVERY power-loss restart) → classified **manual** even inside the power-event window. This is what catches remote/TCL-app offs mid-changeover-chaos (all 3 ACs have `ac_beep_off` rows, so it discriminates house-wide). Known ~30s exposure: right after a real restart beep reads true until beep enforcement re-sends off — a remote off in that gap still reads as power-event (accepted).
  - **Power-event window (15 min, `AC_POWER_EVENT_GRACE_MS`):** the leveler's `onPowerEvent` dep stamps `lastPowerEventAt` on every source change, power-collapse latch, and ESP reading gap > 20s (blackout signature). It also forces the next leveling tick's device fetch (`lastLevelerDevicesFetch = 0`). An observed OFF inside the window → **no lock**; the automation re-turns the AC on with the full active profile (fan/swing intents cleared — the restart reset the device anyway). **The re-on fall-throughs at the metric and range sites re-check the manual-off lock first** (mirroring the schedule site) — locks beat ALL auto-on paths, even the power-event resume.
  - **Power-loss fingerprint:** outside the window, an OFF shadow showing `beep: true` while an `ac_beep_off` row exists (firmware resets beepSwitch ONLY on a power-loss restart — a remote off doesn't), or fan reset to 0 while a fan was commanded, also classifies as power-event.
  - **Commanded-ON shadow-lag grace (2026-07-27 — beats every fingerprint):** an OFF observed within **120s** of a **server-commanded power ON** (`lastServerAcOnAt`, stamped by the leveler's restore dep, automation/schedule turn-ons, timer ONs, and the UI `set_power=1` clear path) is OUR command still in flight — TCL shadows lag ONs by seconds-to-minutes — and never locks; the caller resumes auto-on. **Live trigger:** a leveler restore at 17:15:44 cleared Najat's shed at command SEND (also fixed — shed now clears only on the confirmed shadow ON, `docs/agent/ac-leveling.md` → 2026-07-27 section); 5.8s later the shadow still read OFF, the negative beep fingerprint said "never lost power → manual", and a bogus `observed_off` lock stranded the hot room.
  - **Otherwise → manual:** lock as before, PLUS a critical push through the leveling channel ("AC automation paused") so a wrong guess is a 10-second fix from the phone instead of a hot dawn. (Enable "Smart AC Leveling alerts" per device to receive it.)
  - **`power === undefined` (fetch gap) never locks** — you cannot observe an OFF you didn't see.
  - **Escape hatch:** env `OBSERVED_OFF_LOCKS=false` (config.observedOffLocks) makes observed offs NEVER lock; UI/timer locks unaffected.
  - Regression suite: "observed-off classification — power events vs manual" in `collector.test.ts` (incl. dashboard-off-keeps-lock, beep-false-locks-inside-window, beep-true-still-resumes).
- **The server-on grace is transition-gated, and a lag-window fight locks after one reversal (2026-08-08 — Najat physically cycled on/off after manual offs, nothing visible in the dashboard).** The 120s "shadow lag, not a manual off" fast-path used to be unconditional and ran before every fingerprint — a REMOTE off inside it was reversed with a full `power=1` (re-arming the grace), silently, forever. Now:
  - `noteAcObservedPower` stamps `lastAcObservedOnAt` on every live-observed ON, and the fast-path claims shadow lag ONLY while the shadow has NOT confirmed our server ON (`observedOnAt < serverOnAt`). Once the shadow showed ON and then reads OFF, that is a REAL transition: it falls through to `classifyObservedAcOff` and locks (+pushes) on the FIRST observation.
  - ⚠ The fingerprint deliberately does NOT beat the grace (a design considered and rejected 2026-08-08): a shed room's stale shadow reads exactly `power=0`/`beep=false` — identical to a genuine remote off — so the fingerprint carries no staleness information, and letting it beat the grace would re-open the 2026-07-27 stranding (bogus lock minted during a leveler restore's shadow lag). Staleness is answered by the transition gate, not the fingerprint.
  - Repeat guard (belt, for offs that arrive before the shadow ever confirmed our ON): each grace reversal stamps `acServerOnReversalAt`; a second observed off within `AC_REPEAT_OFF_MANUAL_MS` (10 min) with an ON confirmed IN BETWEEN (`observedOnAt > lastReversal` — a human flipping through the lag; a stale shadow never shows an intervening ON) and OUTSIDE `AC_POWER_EVENT_GRACE_MS` of any power event (hard rule 2: an off near a power event must never record a lock) records the lock and pushes "AC automation paused — repeated off". Cleared whenever the device's lock is recorded or cleared.
  - All new lock paths respect `config.observedOffLocks`. The device-cloud half of the same incident (overlapping binary `set_power` verify loops re-sending against each other) is in [tcl-ac.md](tcl-ac.md) → Last-write-wins verifiers.
- **`clearAcManualOff()`** is called for: UI `set_power=1`, or a **genuine observed physical ON**. As of 2026-06-19 "observed ON" requires BOTH the 15s grace AND that the device's **OFF was actually observed live since the lock** (`acManualOffSeenOff`, set by `noteAcObservedPower` in `getDevicePowerCached`/`reconcileAcManualOffLocks`). A stale/flappy TCL shadow that reports ON without ever reflecting the off can no longer clear the lock — the 32A grid incident (2026-06-19) cleared a sacred lock ~59s after the user's off (grace had passed, but the shadow showed ON the whole time, so the range auto-on turned the AC back on). `recordAcManualOff` resets the seen-off flag (fresh off, shadow may lag); locks **loaded from the DB on startup** are seeded seen-off=true (a prior session's off has long settled). Edge: a sub-shadow-latency off→on toggle where the shadow never shows the off keeps the lock until a real off is observed — erring toward keeping the sacred lock.
- **Every lock release from a commanded ON is announced + audited (2026-07-24).** `clearAcManualOff()` now RETURNS whether this call is the one that released the lock (the underlying `Set.delete` is atomic, so a burst of concurrent turn-ons can't all claim it and multi-push — an `isLocked()`-then-`clear()` pair would have). On a true release the `set_power=1` branch calls `notifyLockCleared(deviceId, authKind, ip)` → `collector.notifyAcLockCleared()`, a **critical** push through the leveling channel ("Najat was turned ON from the dashboard/the Hermes agent (ip) — the manual-off lock is cleared"). Same per-device opt-in as the other leveling pushes. Separately, EVERY AC control request is written to `ac_control_audit` (device, command, value, `auth_kind` user|agent, IP, user-agent — schema in [database.md](database.md)).
  - **Live trigger — "Najat keeps turning back on" (2026-07-23/24, on gen):** four dashboard offs (18:18, 19:01, 00:56, 01:28 UTC) each recorded a `ui` lock correctly and the range automation honored it (42 straight minutes of "manual-off locked, skipping auto-on" before the last one) — **the lock machinery was never bypassed**. Each re-ON chain instead began with an authenticated `POST /api/ac/devices/:id/control {set_power:1}` (bare `[tcl] Control set_power=1` + `Restored last state` + `manual-off lock cleared` within ~1s — the *user ON* path, which by design clears the lock); the hot room then let the range automation finish the turn-on seconds later. Automations, timers, leveler restores and the verify-resend loop were all excluded by log signature, and the household confirms nobody pressed ON. The server logged **no request identity**, and `handleAgentSession` minted a JWT identical to a human login — so "who" was unprovable. Hence the audit table + the `agent` claim; the Hermes agent does control ACs and is the prime suspect. **If the audit confirms it**, the follow-up decision is whether agent-session ONs may clear locks at all (deliberately NOT implemented yet — it would break legitimate "turn mom's AC back on" requests). **Postscript (2026-08-05):** the identical fingerprint recurred for Abdu AC and this time the audit's `user_agent` (the user's own desktop Chrome) plus the user's confirmation resolved it — his own clicks. Hermes was never confirmed for the 07-24 events either (zero session/bearer activity when re-checked); weigh "the user or household clicked and it wasn't connected to the complaint" FIRST before suspecting agents or automations.
- **The commanded ON claims its release BEFORE the send, and observed-ON releases are announced too (2026-08-05).** The `set_power=1` handler used to call `clear()` only *after* `sendControlVerified()` — whose power-on path runs `restoreLastState` with a ~1s delay, so the TCL shadow echoed our own ON early, and the dashboard device-poll's `reconcileAcManualOffLocks()` observed it, won the atomic release, and cleared the lock **silently** (that path was never wired to notify). Live: 2026-08-05 00:42:34, "manual-off lock cleared" 455 ms *before* "Restored last state", no push — the user hunted a ghost that the missing push existed to name. Now the route claims the release (and pushes, with authKind + IP) before the send; deliberate tradeoff: if the send then throws, the lock stays released — the user's latest intent was ON and the 500 reports the failed send. And a genuinely observed-ON release (remote/app/panel, via `reconcileAcManualOffLocks` or `getDevicePowerCached`) now pushes "AC manual-off released" through `notifyObservedAcLockCleared()` — deliberately NOT called from `clearAcManualOff()` itself, because the routes path pushes its own richer message and would double-push. Since every server-side auto-on is lock-gated and the REST path clears first, an observed ON that still finds a lock is guaranteed external. Regression tests: `ac-control-audit.test.ts` "claims the release before the send…", `collector.test.ts` observed-ON release pair.
  - **Live trigger — "Abdu turned back on" (2026-08-05, the 2026-07-23/24 shape again):** dashboard off 00:31:47Z recorded its `ui` lock correctly; the leveler journal is provably silent at both re-ONs (00:42:33 / 01:51:17Z), automations logged "skipping auto-on" up to the moment of each call, Hermes had zero session/bearer activity — each re-ON was an authenticated `POST …/control {set_power:1}`, `auth_kind=user`, household IP, the user's own desktop-Chrome user-agent (from `ac_control_audit`). The lock machinery was again never bypassed — and the user confirmed the clicks were his own. The whole hunt existed because the 00:42 release push was silently swallowed by this race; with the fix, one push would have answered it in seconds.
- A lock **blocks all AC auto-on paths** (metric/range, schedule, turn-on timers) until a manual-on is observed. **Never auto-clear from temperature thresholds** — temperature reaching the low/off limit must NOT unlock it.
- Locked ACs expose `manualOffLocked` from `/api/ac/devices`; the UI shows a lock icon and disables turn-on timers. Turn-on timer creation is rejected with 409 when locked, and an older turn-on timer that fires while locked is skipped.
- **History / superseded design**: the old in-memory mechanism set `canAutoTurnOn=false` on `AutomationState` when a manual off was detected in the dead-zone cooldown check, and unlocked (`canAutoTurnOn=true`) when temp reached the opposite (turn-off) limit. That itself replaced an even older `"override"` status (removed 2026-04-24) with a simpler flag on the existing `"idle"`/`"triggered"` two-state model. **Superseded 2026-06 by persistent DB locks** (CLAUDE.md is authoritative here): `AutomationState.canAutoTurnOn` still exists for legacy/shared state-shape compatibility, but the device locks are the real mechanism — **do not reintroduce temperature-based unlocks**.
- **Shed ≠ manual-off** (leveler interaction; leveler side in [ac-leveling.md](ac-leveling.md)): all observed-off lock recorders and all auto-on paths (metric/range/schedule/timers) skip leveler-shed devices; automation-driven turn-offs (range off, outside-range off, `turn_off_at_end`, timer off) clear the shed flag; a UI power-off converts shed → manual-off lock; an observed external ON clears shed after a 15s grace.

## Schedule-based

- Daily time-window enforcement (e.g., 22:00–07:00 → keep device ON, re-checks every cooldown cycle, default **60s**). Works for both purifiers and ACs. Optional `turn_off_at_end`. Uses `getDevicePowerCached()` with 5s TTL.
- **AC schedules respect manual-off locks**: if a locked AC is OFF during an active window, the schedule skips auto-on; if a triggered schedule later sees the AC manually off, it records the lock.
- Both start and end times support two modes:
  - **Exact**: fixed HH:MM time (stored in `time_start`/`time_end`).
  - **Prayer-relative**: dynamic time based on daily prayer calculation (e.g., "30 min before Fajr"). Uses `start_mode`/`end_mode` (`'exact'`|`'prayer'`), `start_prayer`/`end_prayer` (prayer name), `start_prayer_offset`/`end_prayer_offset` (signed minutes, -120 to +120). Prayer times are resolved via `resolvePrayerMinutes()` in the collector using cached prayer times from the `prayer-engine` (`getBaghdadPrayerTimes()` via `prayer.ts`, `BaghdadYMA` profile — same source as alerts and the public endpoint). `ensurePrayerTimesForToday()` caches prayer times per Baghdad day, independently of alert subscriptions.

## AC Timers

- Server-side countdown timers, **in-memory only** (`acTimers` Map in `server/src/routes.ts`) — lost on container restart.
- API: `GET /api/ac/timers`, `POST /api/ac/timer` (body: deviceId, action on/off, minutes 1–480, optional preset), `DELETE /api/ac/timer/:deviceId`.
- The collector checks timers each cycle via `checkAcTimers()` (skipped while calibration is active — timers stay pending and fire late).
- UI: timer section in the AC detail overlay (visible even when the AC is off), compact countdown indicator on the AC widget capsule (green=turn-on, red=turn-off). `useAcTimers()` hook polls `/api/ac/timers` every 5s. Timer props flow: IndoorSection → DevicesCard → AcWidget → AcDetailOverlay. (An older memory note said IndoorSection → IndoorCard → AcWidget; CLAUDE.md wins — DevicesCard is current.)
- **Turn-off timers are treated as user intent** and create a manual-off lock. **Turn-on timers cannot override** a manual-off lock or a leveler shed (rejected with 409 at creation when locked; skipped if an older timer fires while locked).
- **Leveler integration**: turn-on timer presets have `generator_mode` stripped when the leveler manages the device.

## AC Presets — server-side behavior

(The preset VISUAL UI — the 5×2 grid of detail cards, in-flight glow, active-match ring/`presetMatchesCurrent()` highlight — is documented in [frontend.md](frontend.md); it exists and matches on the 4 visible props only.)

- **10 slots per device** (was 5 until 2026-06-06), stored server-side in the `ac_presets` PostgreSQL table (moved from localStorage 2026-05-01; shared across all browsers/devices). The DB CHECK constraint was widened 5→10 via the idempotent `DROP CONSTRAINT IF EXISTS ac_presets_slot_check` + `ADD CONSTRAINT` migration pair in `database.ts` MIGRATIONS. Table schema in [database.md](database.md).
- API: `GET /api/ac/presets/:deviceId` (returns slots 1–10), `PUT /api/ac/presets/:deviceId/:slot` (validates slot 1–10).
- `PresetData` captures **10 properties**: mode, targetTemp, fanSpeed, eco, turbo, screen, verticalSwing, horizontalSwing, freshAir, generatorMode.
- Frontend slot count derives from the `PRESET_COUNT`/`PRESET_SLOTS` constants in `ac-widget.tsx` — **never hardcode `[1,2,3,4,5]` arrays**.
- **Apply syncs to automations** (added 2026-05-13, reworked 2026-08-16): `POST /api/ac/preset-apply` first applies one server-side capability-filtered profile and confirms its shadow, then updates `action_on` on **ALL enabled AC automations for that device** (no `_preset_slot` filter — the user's explicit apply overrides any automation's configured preset). While confirmation is pending, stale profile/drift re-enforcement is explicitly suppressible for that device; a newer direct UI control, preset, safety action, timer, calibration step, or automation state transition supersedes the pending request instead. Only after successful confirmation does the route call `onAutomationRulesChanged?.()` → `collector.invalidateAutomationRules()`, so the next tick (≤5s) reloads the new profile. Failed/superseded requests do not update automation state.
  - Presets apply **directly on tap** via `applyPreset(slot, p)` in `ac-widget.tsx` (no Apply button). The client sends the single profile request, handles non-2xx failures, and shows an inline error. The sync only triggers on a preset tap — NOT for individual manual control changes.
- **Save syncs** via `POST /api/ac/preset-sync` — updates automations referencing that `_preset_slot`.
- Preset data is copied into `action_on` JSONB (with the `_preset_slot` reference) when creating AC automations.
- **One-time migration from localStorage** runs on first overlay open (legacy browser-stored presets are pushed to the server).

## Sticky beep-off enforcement

Persistent per-AC beep-off preference (added 2026-06-07). The `ac_beep_off` table (`device_id TEXT PRIMARY KEY`, `set_at TIMESTAMPTZ`) schema lives in [database.md](database.md); the behavior:

- **Row present = enforce off**: the collector re-sends `set_beep 0` whenever the AC is observed ON with shadow `beep: true`. Rationale: TCL firmware resets `beepSwitch` to ON after a power-loss restart (mains cuts / changeover) — the pref survives both server and AC restarts.
- **Written via the UI Beep toggle**: `set_beep 0` records the row, `set_beep 1` deletes it — via the `onUserBeep` hook → `collector.noteUserAcBeep()`. Turning Beep off in the AC widget makes it sticky; turning it on releases the pref.
- **Enforced by `checkAcBeepEnforcement()` each collector tick**: 30s per-device resend cooldown; its own 30s-gated `fetchDevicesLive` when the shared device cache is cold (nothing else refreshing it); skipped while calibration is active. Recording the pref stamps the cooldown so the UI's own send isn't doubled.
- **Enforce-OFF only.** Deliberately NOT part of presets/`AcAction`/last-state restore — the table is the single source of truth.

## Fan & swing enforcement sweep (2026-08-06)

`checkAcRangeEnforcement()` — a beep-style sweep, run once per collector tick as its own `ac-enforce` step (after `leveling`, so fan holds and shed flags are that tick's truth). It asks about the fan and the vertical swing exactly what `checkAcBeepEnforcement` asks about the buzzer: does the shadow still carry what the active slot resolves to?

**Why a second path at all.** `checkAcRangeAutomation` only re-enforces along its own state machine, and a device it is *skipping* — shed, an off it never saw, a shadow lagging minutes behind — is exactly the device whose fan came back as built-in auto. The user's complaint was "the system needs to keep checking"; this is that check.

### The motivating incident — Najat stuck on 'A' (2026-08-06, UTC)

02:21 grid→gen (limit 15 A); a heater pushed the non-AC house to 7.4 A at ~02:31; the leveler shed Najat and Abdu and cut Abdullah L2→L1 at 02:32, then restored Najat at 02:33. She came back with `fanSpeed 0` — device built-in auto, "A" on the card — and stayed there, with her range rule enabled and its slot asking for `fan_speed 7`. Three things had to line up:

1. Every leveler **gen restore** pins `fan:1` and records a gentle hold whose `originalFan` is hardcoded 0 (`leveling/fan-trim.ts` `recordGentleRestoreHold`), so the fan-restore climb deliberately ENDS by commanding device-auto and hands the channel back to the range automation.
2. The range automation never took it back, because `acFanEnforcement.manual` was still set from **before** the power cycle. `clearAcFanEnforcement()` / `clearAcSwingOverride()` were called only from `checkAcRangeAutomation`'s own five automation-driven power-cycle sites — and its observed-off branch skips shed devices outright (`isShed → continue`), so a leveler shed reaches no clear site and a leveler restore has no site at all.
3. With `manual` set, `effectiveAcRangeProfile()` deletes `fan_speed` **and** `turbo` from the enforced profile, so nothing re-asserted, forever.

Swing had the same shape with an extra hole: the leveler never writes swing, swing has no drift detection, and its override hung on the same stale-intent gap.

### Power-cycle clear sites

`notePowerCycle(deviceId, reason)` is the shared edge. It **releases the manual flag; it does not delete the entry** — the five rule-owned sites can drop the whole entry because each re-sends the full profile in the same breath and `noteAcFanCommanded` rebuilds it, whereas nothing re-sends here, and the baseline (`lastCommandedFan`/`lastFanCommandAt`) is what `refreshAcFanBaseline()` updates on every leveler fan command and what keeps a later drift check from misreading our own send. Swing overrides carry nothing but intent, so those are deleted. It also stamps `acPowerCycleAt`, which is the swing sweep's firmware-reset window (`AC_POWER_CYCLE_RESET_MS`, 15 min — the same "a shadow can lag minutes" reasoning as `AC_POWER_EVENT_GRACE_MS`).

| Edge | Hook | Note |
|---|---|---|
| Leveler shed | `setDevicePowerCache(id,"off")` dep | The leveler touches that dep on its own shed/restore ONLY, so it is the exact command-time edge |
| Leveler restore | `setDevicePowerCache(id,"on")` dep | The restore has no automation-side site whatsoever — this is its only cover |
| Leveler shed (backstop) | `observeLevelerShedEdges()` in the sweep | Catches sheds the dep can't see: adopted from the DB at boot, a controller flip |
| Changeover / collapse / blackout | `notePowerEvent()` → every cached AC | The units restart; the firmware resets the blower to auto and re-reads swing |

⚠️ **Only the `false→true` shed edge clears.** A shed clears on the **confirmed shadow ON**, 5.8 s–13 min after the restore command (ac-leveling invariant 4) — treating the un-shed edge as the cycle would wipe a manual change the user made minutes after the room was already back. Regression test: "does not treat the un-shed edge as the cycle".

⚠️ **A genuine manual change AFTER the cycle still wins.** Every clear is edge-triggered, so the UI hook (`noteUserAcFanChange`/`noteUserAcSwingChange`) or drift detection re-arms the override on the next user action. The clear only forgets PRE-cycle intent — that is the whole contract.

### The staleness heal — a manual flag on an observed fan 0

`acFanOverrideActive(ruleId, deviceId)` is the single question both `effectiveAcRangeProfile()` and the sweep ask. It answers **false** — and **releases** the entry (`manual: false`, baseline kept; it deleted the entry as first written, fixed on review 2026-08-06) — when the shadow reports `fan_speed 0`, because an observed 0 is the device's BUILT-IN auto and nothing here can have asked for it: range automations never command 0, and the dashboard's **A** button expresses that intent by DELETING the override (`noteUserAcFanAuto`), never by marking it manual. So a `manual` flag sitting on an observed 0 is pre-power-cycle intent the firmware has already eaten — the documented *"until the AC power cycles"* release, read off the firmware's own fingerprint for the cycles no clear site witnessed (a restart, or a cold device cache at power-event time). This is the belt to the clear sites' braces, and it is what makes a stuck 'A' self-heal within one cooldown. Consistent with the existing rule that **observed fan 0 is NEVER a manual intent**, and with its accepted trade-off (a *remote*-set built-in auto is also overridden).

⚠️ **Release, don't delete — `notePowerCycle`'s rule, for its own reason.** This is a read-side predicate: nothing here re-sends the profile, so dropping the entry threw away the baseline `refreshAcFanBaseline()` keeps current on every leveler fan command, and — worse — `driftedRangeFan()` reads that same entry **one line later** for its `AC_FAN_SETTLE_MS` guard, so the predicate destroyed the settle window its own caller was about to consult and re-asserted on top of a send the shadow had not reported yet. Regression: *"the heal RELEASES the entry, it does not delete it"*.

### Gates — what stands the sweep down

Per rule: not an enabled AC range rule · no active slot (the rule owes an OFF, not a fan) · the metric is stale on the same bars the rule itself uses · the metric says the rule is about to turn the device off · **the rule's own `cooldown_secs` has not elapsed since its `lastToggle`**.
Per device: calibration active · device off or not in the shared cache · `leveling().isShed()` · `leveling().hasFanHold()` (the leveler owns the fan channel while it holds it) · our own off inside `AC_OFF_REFIRE_GRACE_MS` · our own turn-on inside `AC_FAN_SETTLE_MS` · a previous sweep send inside `AC_ENFORCE_RESEND_COOLDOWN_MS` (30 s, per device).

⚠️ **The `lastToggle` gate is not redundant with the per-device ones** (added on review, 2026-08-06; the sweep shipped without it). Manual-fan detection lives in `updateAcFanTracking`, and the rule's **turn-on**, **locked-adopt** and **power-event re-turn-on** paths each stamp `lastToggle: now` and `return` *before* tracking runs. Inside `cooldown_secs` of one of those, no tick has yet had the chance to notice a remote/app fan change — so a sweep firing there reverted the user within 30 s and never recorded the override at all, winning a contest he never got to enter. Waiting out the rule's own cooldown guarantees manual detection gets a tick first. Regression: *"waits out the rule's own cooldown, so manual detection gets a tick"*.
Per channel: fan — a live (non-stale) manual override, or our own fan send still inside `AC_FAN_SETTLE_MS`; swing — no slot swing pinned, a live manual swing override, or no power cycle inside `AC_POWER_CYCLE_RESET_MS`.

**Fan and swing are sent as two separate single-property `executeAcAction` calls** — on a TAC-12CHSD the fan block is silently dropped when it shares an update with anything else ([tcl-ac.md](tcl-ac.md) → "the fan block must travel ALONE").

Regression suite: `collector.test.ts` → "AC fan/swing enforcement sweep (2026-08-06)", named case **"regression: Najat fan stuck at device-auto after a leveler shed/restore across a changeover self-heals"**, plus the two review regressions above. Each of the six mechanisms (shed edge, restore hook, power event, staleness heal, release-don't-delete, the `lastToggle` gate) was verified by re-breaking its own line and confirming only the tests that guard it go red. It is also inventoried in [testing.md](testing.md).

## Leveler integration points (automation side)

Leveler internals (budgets, allocator, sheds, fan holds, warm restore mechanics) are in [ac-leveling.md](ac-leveling.md). What the automation code does:

- **Per-automation opt-out**: `automations.smart_leveling BOOLEAN DEFAULT true` (AC rules only). When **false** (checkbox in the AC trigger form), the automation keeps sending `generator_mode` from its preset and the leveler counts the AC's draw but never adjusts/sheds it. When **true** + leveler enabled, `stripGenIfLeveled()` removes `generator_mode` from turn-on profiles and at all **3** `computeAcDiff` re-enforcement sites. **Gotcha**: opt-out only applies while the rule is **enabled** — a disabled rule means the leveler manages the device.
- **`stripLeveledControls(rule, action, deviceId)`** wraps `stripGenIfLeveled` and additionally strips `fan_speed`+`turbo` at the turn-on + 3 re-enforcement sites while a leveler fan hold is active (see Range slots & fan above for the full fan-hold deference behavior, incl. `refreshAcFanBaseline()`).
- **Shed vs manual-off**: leveler-shed devices are skipped by all observed-off lock recorders and all auto-on paths (metric/range/schedule/timers); automation-driven turn-offs (range off, outside-range, `turn_off_at_end`, timer off) clear the shed flag; UI power-off converts shed → manual-off lock; observed external ON clears shed after a 15s grace.
- **Timers**: turn-on timer presets have `generator_mode` stripped when the leveler manages the device; turn-on timers cannot override a leveler shed.
- **Warm-restore hook**: temperature-cycle auto-offs in `checkAcRangeAutomation` call `acLeveler.rememberStableLevel(did)` before the off command (scoped to temperature cycling only — not schedule/time-window ends, not manual-off, not sheds).
- **Manual fan change hooks**: `collector.noteUserAcFanChange()` also releases any leveler fan hold via `acLeveler.onUserFanChange`; `collector.noteUserAcFanAuto()` likewise releases a hold.
- **Leveler power cycles clear fan/swing intent** (2026-08-06): the `setDevicePowerCache` dep — which the leveler touches on its own shed and restore ONLY — routes through `notePowerCycle()`, and the collector observes `isShed` false→true edges in its own tick as a backstop. Neither a shed nor a restore reaches any of the five rule-owned clear sites, which is how an AC ends up parked on device-auto after a shed/restore. Full write-up: "Fan & swing enforcement sweep" above.

## Fixed bugs (history)

### Xiaomi 2FA re-auth froze the whole automation loop — FIXED 2026-07-02

The in-loop Xiaomi re-auth in `checkAutomations()` was `await`ed. When the Xiaomi session expired (401) and re-login demanded a 2FA code, `xiaomiCloud.init()` blocked indefinitely (its `on2fa` callback resolves only via `POST /api/xiaomi/verify`), freezing the entire `collectAll` loop — weather, alerts/push, AC schedule/metric automations, timers, beep enforcement, and calibration all stopped for ~4h. Only air (MQTT), power (ESP `POST`), and urgent AC leveling (power-ingest triggered) kept running, masking it. **Fix**: the re-auth is now **fire-and-forget** (`void this.xiaomiCloud.init().catch(...)`, `xiaomiRetryAt` set before launch), so a pending 2FA prompt never blocks automations — purifiers simply stay unmanaged until the code is submitted. Guard `status !== "needs_2fa"/"needs_captcha"` prevents relaunch spam. Full write-up + the loop-must-never-block principle in `architecture.md` → Known Bugs. Regression test: `collector.test.ts` "in-loop Xiaomi re-auth does not block the collection loop".

### Dead-zone status clobber — FIXED 2026-06-10

The **idle + dead-zone adoption** branch of `checkAcRangeAutomation()` set `status: "triggered"` inside the device loop, but a trailing `if (state.status === "idle")` write with the **stale local `state` object** clobbered it back to idle — so the adoption path re-ran every 5s tick (repeating "adopting with diff" logs; behavior converged since both paths diff-enforce).

**Fix**: a local `adopted` flag — the trailing write only happens when no device was adopted (`if (!adopted) set({...state, conditionSince: null})`). **Fan-enforcement clear placement outcome**: adoption still does NOT clear `acFanEnforcement` — manual fan overrides clear only on slot change / power cycle / automation turn-on (pinned by the regression test `manual fan override survives dead-zone adoption`).

### Double turn-off re-fire — FIXED 2026-06-10

The triggered turn-off didn't stamp `devicePowerCache` "off"; the shadow lags past the 5s cache TTL, so ~7s later the idle branch saw the device "ON past turn-off limit" and re-fired the off (+ a second `rememberStableLevel`) — seen live 2026-06-09. **Fix**: `acRangeOffAt` map + `AC_OFF_REFIRE_GRACE_MS` 15s — all 3 automation off sites (triggered turn-off, idle past-limit, outside-range) stamp it and the re-fire paths skip inside the grace; the triggered site also stamps the power cache now. Past the grace a genuinely still-ON AC is retried (Najat sometimes needs commands re-done).
