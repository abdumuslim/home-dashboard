# Database Schema

TL;DR: The app uses a PostgreSQL database named `home` running on the shared, pre-existing `rag-postgres-1` container (pgvector:pg16) on the VPS; the database is auto-created on first startup. Schema init and migrations live in `server/src/database.ts`. Time-series tables are keyed by `ts TIMESTAMPTZ` with BRIN indexes. For the in-memory 1-minute median buffering that feeds these tables, see [architecture.md](architecture.md); for behavior built on these tables see [ac-automations.md](ac-automations.md) and [ac-leveling.md](ac-leveling.md).

## Tables

Main tables in the `home` database:

- `weather_readings` — 32 columns, keyed by `ts TIMESTAMPTZ` with BRIN index (metric units, all conversions done at collection time). Includes outdoor, indoor console, and ch8 "Abdu" sensor data.
- `air_readings` — 9 columns, keyed by `ts TIMESTAMPTZ` with BRIN index
- `alert_rules` — per-subscription alert configurations (FK to `push_subscriptions.endpoint` with CASCADE). Fields: `alert_type` (sensor/prayer), `metric`, `condition` (above/below), `threshold`, `prayer_timing` (at_time/before), `prayer_minutes`, `prayer_names TEXT[]`.
- `automations` — Device automation rules (purifiers + ACs). Fields: `id`, `automation_type` (metric/schedule), `device_type` (purifier/ac), `device_ids`, `device_names`, `metric`, `condition`, `threshold`, `threshold_low` (AC range hysteresis), `sustained_minutes` (metric type), `time_start`, `time_end`, `turn_off_at_end` (both types), `start_mode`, `start_prayer`, `start_prayer_offset`, `end_mode`, `end_prayer`, `end_prayer_offset` (schedule type), `action_on` (JSONB — purifier: `{power:"on"}`, AC: full preset profile `{power:1, mode, temperature, fan_speed, eco, turbo, screen, vertical_swing, horizontal_swing, fresh_air, generator_mode}`), `action_off`, `cooldown_secs`, `enabled`.
- `power_readings` — 6 columns (ts, voltage, current_1, current_2, power_1, power_2), keyed by `ts TIMESTAMPTZ` with BRIN index. `current_1` = grid, `current_2` = generator. **Rows are a 60-second MEDIAN of the ~3–5 s ESP stream** (`routes.ts` buffers and persists once per `POWER_SAVE_INTERVAL`), so sub-minute events — a power-collapse cliff, a compressor ramp — are invisible here; the leveler itself sees every raw reading. For sub-minute forensics use the container logs or `ac_leveling_journal` (`operations.md` → journal forensics).
- `tuya_power_readings` — mirror of `power_readings` (same 6 columns, `ts` PK, BRIN index) for the **Tuya SHADOW feed** (ESP-replacement P2, 2026-08-18). Written ONLY by `POST /api/power/tuya-ingest` (`server/src/tuya-power.ts`), 60-second medians of the ~2.6 s sidecar stream. Deliberately separate from `power_readings` so the ESP/leveler path stays untouched; used for the P3 side-by-side comparison.
- `ac_presets` — Server-side AC preset storage. Composite PK `(device_id, slot)`. Fields: `device_id TEXT`, `slot SMALLINT` (1-10), `data JSONB` (PresetData shape), `updated_at TIMESTAMPTZ`. Max 30 rows (3 devices × 10 slots). Slot range widened 5→10 (2026-06-06) via idempotent `ALTER TABLE ... DROP CONSTRAINT IF EXISTS ac_presets_slot_check` + `ADD CONSTRAINT` migration entries — this DROP/ADD pair is the pattern for changing CHECK constraints on existing tables (CREATE TABLE IF NOT EXISTS won't update them).
- `ac_manual_off_locks` — Persistent AC manual-off intent. Fields: `device_id TEXT PRIMARY KEY`, `locked_at TIMESTAMPTZ`, `reason TEXT`. This table prevents deploys/restarts from clearing a user's manual-off choice. Never auto-clear from temperature thresholds; clear only on explicit/observed manual-on.
- `ac_beep_off` — Persistent per-AC beep-off preference. Fields: `device_id TEXT PRIMARY KEY`, `set_at TIMESTAMPTZ`. Row present = collector re-sends `set_beep 0` whenever the AC is observed ON with shadow `beep: true` (TCL firmware resets `beepSwitch` to ON after a power-loss restart). Written via UI Beep toggle (`set_beep 0` records, `set_beep 1` deletes — `onUserBeep` hook → `collector.noteUserAcBeep()`). Enforced by `checkAcBeepEnforcement()` each tick: 30s per-device resend cooldown, own 30s-gated `fetchDevicesLive` when the shared cache is cold, skipped while calibration is active. Deliberately NOT part of presets/`AcAction`/last-state restore — single source of truth.
- `ac_leveling_config` — Smart AC Leveling config. Single row (`id SMALLINT PRIMARY KEY CHECK (id = 1)`), `config JSONB` (enabled, gridLimitAmps, genLimitAmps, marginAmps, raiseBufferAmps (raise-side hysteresis deadband, default 1A — see the "Raise hysteresis buffer" section in [ac-leveling.md](ac-leveling.md)), comfortTargetC, priority[], ampModels{} (grid + fallback), genAmpModels{} (optional, used on generator), levelBoosts{deviceId: {minLevel, outdoorAtLeastC}}, maxRaiseStepGrid/maxRaiseStepGen (optional, default 1 — levels an AC may be raised per batch per source; one-step pacing, see the "Grid raise discipline" section in [ac-leveling.md](ac-leveling.md))), `updated_at`. New fields reach existing rows via the load/save default-merge (no migration).
- `ac_leveling_costs` — Leveling v2 learned per-transition costs. PK `(device_id, source, transition)`; `transition` e.g. `level:1>2`, `on@L1`, `fan:step`; `ewma_amps REAL`, `samples INT`, `updated_at`. Survives deploys/config saves (the v1 in-memory maps were wiped on both); seeded once from the 2026-07 mined values when empty; reset only via `POST /api/ac/leveling/costs/reset`.
- `ac_leveling_journal` — Leveling v2 command-outcome journal (~250 rows/day, BRIN on `at`, 60-day prune). Every planned batch: `source, mode, severity, reason, required_amps, pre_amps, commands JSONB, decisions JSONB, expected_delta, executed` (false = shadow decision), graded outcome (`graded_at, post_amps, observed_delta`). Read via `GET /api/ac/leveling/journal?hours=N` (returns `{hours, entries[]}`, not a bare array). Single-actuator graded batches feed `ac_leveling_costs`. **`expected_delta` is only set on reduce batches** — raise/floors/grid_full leave it null and are graded per-command, so comparing a raise's priced cost to its outcome means parsing the acted decision's `detail` string.
- `ac_leveling_config` **row id=2** — Leveling v2-owned fields (`controller` flag, `restingBufferAmps`, `raiseCalmSeconds`, `restoreCalmSeconds`, `fanTrimEnabled`). v2 merges row 1 + row 2 (2 wins); v1 only ever writes row 1, so a v1 config save can't clobber the flag. **Since 2026-08-03 v2 also writes row 1** (non-v2 fields, MERGED over the stored row — never replaced): `collector.leveling()` routes every save to the acting controller, and v2's save path only persisting its own five keys made every dashboard config save a silent no-op for the ten days after the cutover (amp models, limits, boosts and priority vanished behind a `200`; row 1's `updated_at` still read 2026-07-24). Forensic corollary: never trust a config value because a past session set it — re-read it.
- `ac_leveling_shed` — ACs powered off by the leveler (NOT manual-off). Fields: `device_id TEXT PRIMARY KEY`, `shed_at TIMESTAMPTZ`, `reason TEXT`. Survives restarts so a shed AC is still auto-restored after a deploy. Cleared on restore, user power on/off, automation-driven off, or observed external ON (15s grace).
- `ac_leveling_fan_hold` — Leveler fan holds (fans reduced to minimum as the last try before a shed). Fields: `device_id TEXT PRIMARY KEY`, `original_fan SMALLINT`, `last_set_fan SMALLINT`, `held_at TIMESTAMPTZ`. Survives restarts so the staged fan restore resumes after a deploy (otherwise automation-less ACs would stay stuck at fan 1 invisibly). Cleared on full restore, user/external fan change, shed, power-off, or leveler disable.
- `ac_leveling_remembered_level` — Stable gen level captured on a temperature-cycling auto-off for fast warm-restore on return. Fields: `device_id TEXT PRIMARY KEY`, `level SMALLINT`, `remembered_at TIMESTAMPTZ`. Survives restarts so a deploy mid-cycle doesn't force a slow re-climb. Written by `rememberStableLevel()` (only for levels ≥ 2); cleared on reaching the level, manual gen/power change, or shed.
- `ac_leveling_level_hold` — Leveling v2 **learned non-cooling hold** (2026-08-04). Fields: `device_id TEXT PRIMARY KEY`, `level SMALLINT` (the level observed not to cool — always 1 today), `outdoor_c REAL` (`T_obs`, the outdoor temperature the observation was made at), `observed_at TIMESTAMPTZ`. Written when the system observes a level failing to cool (a graded lone off whose drop measured about a fan; the sub-floor-watch armer was removed 2026-08-06) or when the user raises the room off that level by hand, and since 2026-09-24 **only for a room with a configured `levelBoosts` entry** (`levelHoldAllowed`; a boost-less room's row never binds and is deleted on the next acting tick); the hold bans the level as an automatic target while outdoor ≥ `T_obs − 0.5` and the record is under 6 h old, composing with `levelBoosts` via `max`. **Persisted deliberately**: a 6-hour hold that a deploy erases is a trap — see [ac-leveling.md](ac-leveling.md) → 2026-08-04 and SKILL invariant 52. Row deleted when the weather drops back under the bar or the TTL lapses.
- `ac_calibration_results` — Per-AC measured draw per step. Composite PK `(device_id, source, kind, step)`; `source` 'grid'|'gen', `kind` 'level'|'fan', `step` (level 1–3 since the 2026-06 TCL level removal / fan 1–7), `amps REAL` (median(samples) − all-off baseline), `voltage REAL`, `stddev REAL`, `samples SMALLINT`, `measured_at`. Upsert on re-run (latest measurement wins). Read by `GET /api/ac/calibration` which also derives `suggestedFit` (least-squares base/step per device+source). On 2026-08-19 Abdu's (`CA5IMhFAAAE`) rows were replaced with CT02-clamp-mined per-state values (minus-standby-baseline semantics preserved, real stddev/sample counts) and the 2026-06 contaminated gen fan rows 2/4/5/7 deleted — provenance in `ac-leveling.md` → "2026-08-19 — CT02 clamp measurement".
- `ac_control_audit` — Who commanded each AC. Fields: `id BIGSERIAL PK`, `at TIMESTAMPTZ` (BRIN), `device_id`, `command`, `value TEXT` (JSON), `auth_kind TEXT` (`user` = human dashboard login, `agent` = Hermes session/bearer — see the `agent` JWT claim in [architecture.md](architecture.md)), `ip` (Cloudflare `cf-connecting-ip`, else the socket peer — `x-forwarded-for` is deliberately NOT trusted: its leftmost entry is client-supplied and this is an audit record), `user_agent`. Written fire-and-forget by `POST /api/ac/devices/:id/control` (covers preset taps — they go through the same endpoint); a failed insert never blocks the command. Opportunistic 30-day prune on the same request path (once/day). **Why it exists:** the 2026-07-24 "Najat keeps turning back on" incident was a series of authenticated `set_power=1` calls the server could not attribute, and docker logs rotate in ~1.5 days — see [ac-automations.md](ac-automations.md) → Manual-off locks.
- `ac_leveling_config_audit` — Who changed Smart AC Leveling config. Fields: `id BIGSERIAL PK`, `at TIMESTAMPTZ` (BRIN), `auth_kind TEXT` (`user`/`agent`, nullable), `ip`, `user_agent`, `changed_keys TEXT[]` (top-level config keys whose JSON differs — `computeChangedKeys()` in `leveling-config-audit.ts`), `enabled_before`/`enabled_after BOOLEAN`. Written fire-and-forget by `PUT /api/ac/leveling`; a failed insert never blocks the save. Opportunistic 30-day prune on the same request path (once/day). **Why it exists:** on 2026-08-06 someone disabled the whole controller from the dashboard and it stayed off 7h12m with nothing to attribute it — that PUT was neither audited nor logged, unlike `ac_control_audit` for per-AC commands. "A shed must be LOUD," so an `enabled` flip also fires a leveling-alerts push (OFF critical, ON an all-clear). See [ac-leveling.md](ac-leveling.md) → 2026-08-07 and SKILL invariants 63–66.
- `automations.smart_leveling BOOLEAN DEFAULT true` — per-automation opt-out from leveling (AC rules only).

Other tables referenced elsewhere: `push_subscriptions` (Web Push subscriptions, synced on page load; `alert_rules` FKs to its `endpoint` — see the Push Notifications bullet in [architecture.md](architecture.md)). Columns: `endpoint TEXT UNIQUE`, `subscription JSONB`, `breakpoints INTEGER[]` (legacy), `created_at`, and `leveling_notifications BOOLEAN NOT NULL DEFAULT false` — per-device opt-in for Smart AC Leveling/calibration pushes; `broadcastPush` filters on it (`GET`/`POST /api/push/leveling`).

## Migrations & Conventions

- New columns/tables are added via the `MIGRATIONS` list in `database.ts`.
- **CHECK-constraint change pattern**: `CREATE TABLE IF NOT EXISTS` will NOT update an existing table's CHECK constraint. Use idempotent paired migration entries: `ALTER TABLE ... DROP CONSTRAINT IF EXISTS <name>` followed by `ALTER TABLE ... ADD CONSTRAINT <name> CHECK (...)` (this is how `ac_presets_slot_check` was widened from slots 1–5 to 1–10 on 2026-06-06).
- Deduplication on time-series inserts: `ON CONFLICT (ts) DO NOTHING`.
- The 30-day history endpoint downsamples to hourly averages.

## Known Schema Gotchas

- `air_readings` uses SMALLINT columns (co2, pm25, pm10, tvoc, noise, battery) — the 1-minute median writer can produce fractional values like `692.5` and fail the insert; see "Known Bugs" in [architecture.md](architecture.md).
- `power_readings` numeric columns are REAL, so fractional medians are fine there.
